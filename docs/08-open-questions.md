# 08 开放问题与假设

以下问题在实现前需要产品/用户确认；当前文档已采用“默认假设”，如与预期不符，只需修改对应文档。

## 1. 插件命名与 UI 入口

- **问题**：插件正式名称是什么？UI 入口放在“设置页 `settings.section`”还是侧边栏/其他槽位？
- **当前假设**：`@galactus/kabutack`；设置页新增“角色管理”分区。
- **影响**：`package.json`、路由前缀、UI 注册代码。

## 2. 角色作用域

- **问题**：角色是“全局（所有工作区/会话）”还是“按工作区/项目”？
- **当前假设**：全局，存储在 `~/.dsh/kabutack/roles.json`。
- **影响**：数据模型、激活逻辑、UI 展示。

## 3. “卸载”语义

- **问题**：对插件/MCP/技能，“卸载”是彻底删除还是移到回收站/仅从受管集合移除？
- **当前假设**：
  - 官方/bundle 插件：不可卸载，只能停用。
  - 本插件创建的 MCP/注入插件：从 Loader 与持久配置移除。
  - 文件系统技能：移入 `~/.dsh/kabutack/trash/` 可恢复。
- **影响**：安全边界与 UI 文案。

## 4. 技能“停用”的实现方式

- **问题**：停用技能是直接改 `SKILL.md` frontmatter，还是通过 overlay provider 过滤？
- **当前假设**：文件系统技能直接改 frontmatter；运行时技能用 overlay provider。
- **影响**：`skills-ops.ts` 实现复杂度；对第三方技能的可管理性。

## 5. MCP 定义库与角色关系

- **问题**：MCP 配置是全局定义库（角色引用 serverName），还是每个角色内嵌完整配置？
- **当前假设**：全局定义库 `roles.json.mcps`，角色只引用 `serverName`。
- **影响**：数据模型、角色编辑器 UI、MCP 重复配置管理。

## 6. 自动激活失败策略

- **问题**：DSH 启动时自动激活上次角色，若失败应如何处理？
- **当前假设**：只记录日志，不阻塞 DSH 启动；UI 显示上次失败状态。
- **影响**：启动流程稳定性。

## 7. 是否支持“安装新插件包”

- **问题**：是否需要在管理界面中从本地路径安装/注入新插件？
- **当前假设**：v1 只管理已安装能力；不实现安装向导（可复用 `dsh-super-injector` 的注入能力）。
- **影响**：Phase 范围、API 数量。

## 8. 使用 `ctx.storage` 还是直接文件

- **问题**：角色持久化是否接入 `ctx.storage`（JSON backend）？
- **当前假设**：直接使用 `~/.dsh/kabutack/roles.json`，简单可控。
- **影响**：代码依赖与测试方式。

## 9. UI 技术栈

- **问题**：Client UI 用原生 DOM 还是 React？
- **当前假设**：原生 DOM + fetch，与 `dsh-super-injector` 一致，降低构建复杂度。
- **影响**：`src/client/index.ts` 编写方式与依赖。

## 10. 是否支持“未安装但角色需要”的能力自动安装

- **问题**：角色引用了当前未安装的插件/MCP，是否尝试自动安装？
- **当前假设**：不自动安装；只产生 warning，用户需先安装。
- **影响**：ApplyPlan 的 warning 逻辑与用户体验。
